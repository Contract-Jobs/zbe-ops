# Exhaustive API Feature Details and Constraints (v2)

This documents the **current** API — `app/api`. It replaces `api.md`, which documents the retired system for historical reference only — the two are **not** interchangeable: different tables, different data model (unified inventory items instead of separate material/equipment catalogs, movements instead of logs, individually- vs quantity-tracked equipment as a first-class split), different RBAC resource names in places.

## Global List Parameters (ListParams)

Most list endpoints support:

- **`page`**: default 1.
- **`limit`**: default varies by endpoint — most catalog/master-data endpoints (inventory items, equipment, sites, licenses, tenders, warehouses) default to **10**; movement/task/ledger/transaction/approval listings built on `getListParams`/`getPagination` default to **20**.
- **`search`** (or `q` on `getListParams`-based endpoints): fuzzy text match on key fields.
- **`sortBy`** / **`sortOrder`** (`asc`|`desc`): only on endpoints explicitly documented below as supporting it — many list endpoints in this API are unsorted (insertion order) or have a single fixed default sort.
- **Filters**: on `getListParams`-based endpoints, any other query key becomes a filter; multi-value filters are comma-separated in one query param (e.g. `?status=active,closed`), not repeated keys.

## Global Error Responses

Unchanged from the legacy system — `withV2Service` (`lib/v2_services/handler.ts`) shares the same `handleServiceError` (`lib/api/handler.ts`) as the old `withService`, so both route surfaces map errors identically:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Invalid request payload",
    "details": [{ "path": ["name"], "message": "Required" }]
  }
}
```

- `400` → `VALIDATION_FAILED` (Zod errors, or a service throwing an `Error` prefixed `VALIDATION:`).
- `401` → `UNAUTHORIZED` (no/invalid session).
- `403` → `FORBIDDEN` (RBAC, or a service throwing `Error` prefixed `FORBIDDEN:`).
- `404` → `NOT_FOUND` (service throws `Error` prefixed `NOT_FOUND:`).
- `409` → `CONFLICT` (service throws `Error` prefixed `CONFLICT:` — e.g. closing a site with active inventory).
- `500` → `INTERNAL_ERROR` (unhandled exception).

A successful response is always `{ success: true, data: ... }` — `withV2Service` wraps whatever a route handler returns in `{ data: <result> }` unless the result already has its own `data` key (some services return `{ data, pagination }` shapes directly), or the handler returns a raw `Response` (used for `204 No Content` on deletes).

## RBAC Model

Three roles: `site_manager`, `admin`, `superadmin` (`lib/auth/access-control.ts`). `admin`/`superadmin` have full CRUD+approve on every resource; `site_manager` is scoped as follows — **note the resource names, some of which don't map 1:1 onto a route group**:

| Resource       | site_manager grants       | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tender`       | read                      |                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `site`         | read, update              | Reassigning a site's `managerId`/`tenderId`/`licenseId` is admin-only even for `update` — see Sites.                                                                                                                                                                                                                                                                                                                                                |
| `asset`        | read                      | Governs individual-equipment **CRUD** (`/equipment*`) — a site_manager can list/view equipment but not create/update/delete/restore it directly.                                                                                                                                                                                                                                                                                                    |
| `warehouse`    | read                      |                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `license`      | read                      |                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `inventory`    | create, read, **approve** | Governs the catalog (`/inventory-items`), inventory nodes (`/inventories`), balances, **and all movement creation** — both quantity movements (`/inventory-movements`) _and_ individual-equipment movements (`/equipment-movements`) check `can(role, "create", "inventory")`, not `asset`. So a site_manager can purchase/sell/transfer equipment via a movement even though they can't touch the equipment record directly via `/equipment/[id]`. |
| `transaction`  | create, read              | No `approve` — manual transactions always need an admin to resolve, even a site_manager's own.                                                                                                                                                                                                                                                                                                                                                      |
| `progress_log` | create, read, update      | Governs site tasks.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `budget`       | read                      |                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `approval`     | create, read              | No blanket `approve` — see the site-manager fallback below.                                                                                                                                                                                                                                                                                                                                                                                         |
| `rental`       | create, read, **approve** |                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

**Site-manager approval fallback** (`ApprovalService.assertCanResolve`): even without the generic `approve` grant on `approval`, a site_manager may resolve (`approve`/`reject`) a **pending** `inventory_movement`, `equipment_movement`, or `rental_event` approval if they manage the site the record's destination inventory (or rental agreement) resolves to. A warehouse-anchored record has no site_manager fallback at all (only admin/superadmin can resolve it). `transaction`/`progress_log` approvals are never resolvable by a site_manager this way — `progress_log`'s completion is a distinct admin-only act (`SiteService.completeTask`), separate from a site_manager's own `claimTaskCompletion`.

**The stage → approve → commit pattern**: every mutating action that has real financial/state consequences (movements, rentals, manual transactions, task completion) is staged first (`isApproved: false`), an `approvals` row is created, and then either auto-approved inline (admin/superadmin submitter) or left pending for a separate resolve call. Reversing an **equipment or inventory movement** is the one exception — it always commits immediately regardless of role (gated only by the base `create:inventory` permission), since `IndividualMovementHandler.createReversal`/`InventoryMovementHandler.createReversal` don't stage through the approval system at all.

#### Quantity Movement Payloads (discriminated by `movementType`)

- **`purchase`**: `{ itemId: string | undefined (required unless autoCreateItem given), quantity: number, destinationInventoryId: string, unitCost: string, clientName?: string, licenseId: string, autoCreateItem?: { name, slug?, category: "material", unit? } }` — source is never accepted (always external).
- **`sale`**: `{ itemId, quantity, sourceInventoryId: string, unitCost: string, clientName?, licenseId: string }` — **`sourceInventoryId` must resolve to a warehouse, never a site** (enforced server-side; a 400 results otherwise — sites don't sell anything).
- **`transfer`**: `{ itemId, quantity, sourceInventoryId: string, destinationInventoryId: string }` — can legitimately be site↔site, warehouse↔site, or warehouse↔warehouse; source and destination must differ.
- **`consume`**: `{ itemId, quantity, sourceInventoryId: string }` — material consumption is ledger-inert (cost was already recognized on arrival); bulk-equipment consumption is where its cost actually gets recognized.
- **`loss`**: `{ itemId, quantity, sourceInventoryId: string, metadata: { reason: string } }` — routed to `InventoryLossService.createLoss`, which enforces a non-empty `reason` and is the **only** way to create a `loss` movement (the generic movement path refuses it outright). No `unitCost` accepted — priced from the source balance's current weighted-average cost at commit.

`quantity` is always a positive integer; `movementDate` is not exposed on any of these — backdating exists in the underlying validator but isn't wired up to the API.

#### Equipment Movement Payloads (discriminated by `movementType`)

- **`purchase`**: `{ individualItemId: string | undefined (required unless autoCreateEquipment given), destinationInventoryId: string, movementCost?: string, clientName?: string, licenseId: string, autoCreateEquipment?: { itemId?, autoCreateItem?: {name, slug?, category:"equipment", compositionType?}, identifier?, vendorName?, originalValue, bookValue? } }`. Initial `assignmentStatus` is derived from the destination's type: a **site** destination → `deployed_to_site`; a **warehouse** destination → `idle`.
- **`deploy_to_site`**: `{ individualItemId, destinationInventoryId: string }` — source is derived server-side from the equipment's current location, never client-supplied. Requires current `assignmentStatus = idle`.
- **`return_to_warehouse`**: `{ individualItemId, destinationInventoryId: string }` — requires current `assignmentStatus = deployed_to_site`.
- **`transfer_between_sites`**: `{ individualItemId, destinationInventoryId: string }` — requires current `assignmentStatus = deployed_to_site`; destination must differ from current location.
- **`send_to_maintenance`**: `{ individualItemId, clientName?: string }` — condition-only (requires `condition = ok`); does not touch assignment or location.
- **`return_from_maintenance`**: `{ individualItemId, destinationInventoryId: string, movementCost?: string, licenseId?: string }` — requires current `condition = under_maintenance`. `licenseId` is only required if `movementCost` is actually nonzero (a real repair cost); a free return needs neither and creates no financial transaction at all. Resulting `assignmentStatus` is derived from the destination's type, same rule as `purchase` — can come back to a **different kind** of location than it left from (e.g. picked up from a site, returned to a warehouse).
- **`sale`**: `{ individualItemId, movementCost?: string, clientName?: string, licenseId: string }` — source (derived server-side) **must resolve to a warehouse, never a site**; requires current `assignmentStatus = idle`.
- **`dispose`**: `{ individualItemId }` — terminal; sets `lifecycleStatus = disposed`, `condition = out_of_commission`. No further operational movement permitted afterward.
- **`degrade`**: `{ individualItemId, movementCost: string }` — a pure value write-down (reduces `bookValue`); does not touch location/assignment/condition/lifecycle.

`sourceInventoryId` is **never** accepted from the client for any of the above (removed deliberately — the equipment's own `currentInventoryId` is the only legitimate source, server-derived). `rent_to_client`/`return_from_client`/`rent_from_client`/`return_to_client` are valid `EquipmentMovementType`s but are only reachable via `/rentals`, never this endpoint directly.
